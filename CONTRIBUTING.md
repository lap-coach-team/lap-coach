# Як ми працюємо з GitHub і Jira

Кожна задача з Jira проходить один шлях:

```
задача в Jira → гілка → коміти → pull request → рев'ю ліда → merge → задача Done
```

GitHub підключено до Jira. Якщо в назві гілки, коміту чи PR є ключ задачі (наприклад, `LC-12`), Jira сама показує їх у задачі в блоці **Development**. Так лід бачить, хто що робить, не питаючи.

## Коротко: 5 правил

1. **Одна задача — одна гілка — один PR.**
2. **У назві гілки, коміту і PR є ключ задачі** — `LC-12`. Ключ є на картці в Jira.
3. **У `main` напряму не пушимо.** Тільки через PR.
4. **PR мерджить лід** після рев'ю.
5. **Перед початком роботи оновлюємо `main`.**

## Назви

| Що | Формат | Приклад |
|---|---|---|
| **Гілка** | `<тип>/<КЛЮЧ>-<коротко>` | `planning/LC-12-roadmap` |
| **Коміт** | `<область>:: <КЛЮЧ> <Що зроблено>` | `stage-3:: LC-12 Added Gantt chart to Roadmap.md` |
| **PR** | як коміт | `stage-3:: LC-12 Added Roadmap.md` |

**Типи гілок:** `planning` — документи етапів; `feature` — нова функція продукту; `fix` — виправлення; `chore` — README, `.gitignore`, налаштування.

**Області в комітах:** `stage-N` — матеріали етапу; `chore` — службові зміни; для коду — назва модуля (`telemetry`, `ui`, …).

**Опис коміту** — англійською, у минулому часі, з великої літери: `Added`, `Updated`, `Fixed`, `Removed`. Так уже записана вся історія репозиторію.

## Покроково

### 1. Почати задачу

1. У Jira перетягніть задачу в **In Progress**.
2. Оновіть `main` і створіть гілку:

```bash
git switch main
git pull
git switch -c planning/LC-12-roadmap
```

### 2. Працювати

Комітьте невеликими кроками, кожен коміт з ключем задачі:

```bash
git add docs/stages/stage-3/Roadmap.md
git commit -m "stage-3:: LC-12 Added list of work packages"
git push -u origin planning/LC-12-roadmap
```

Перший `push` з `-u`, далі достатньо просто `git push`. Пуште хоча б раз на день, навіть незавершене: лід бачить прогрес у Jira.

### 3. Відкрити pull request

1. На GitHub натисніть **Compare & pull request**.
2. **Base:** `main`. **Назва:** у форматі коміту, з ключем.
3. **Reviewers:** лід.
4. В описі коротко: що зроблено і що лід має перевірити. Якщо щось не встигли — так і напишіть.
5. У Jira перетягніть задачу в **Review**.

Якщо робота ще не готова, але хочеться показати, відкрийте **Draft pull request**.

### 4. Рев'ю і правки

Лід лишає коментарі в PR. Виправте у тій самій гілці й запуште — PR оновиться сам. Коли все гаразд, лід мерджить PR, а задача в Jira переходить у **Done**.

### 5. Якщо `main` пішов уперед або є конфлікт

```bash
git switch main
git pull
git switch planning/LC-12-roadmap
git merge main
```

Якщо git пише про конфлікт — відкрийте файл, знайдіть блоки `<<<<<<<` і `>>>>>>>`, залиште правильний варіант, потім `git add` і `git commit`. Не впевнені — напишіть ліду, не робіть `git push --force`.

## Що не комітимо

- **Файли збирання LaTeX** (`.aux`, `.log`, `.toc` і т. д.) — вони вже в `.gitignore`.
- **Проміжні PDF.** Комітимо лише фінальний PDF разом із його джерелом (`.tex`).
- **Паролі, токени, ключі API.**
- **Великі відео.** Для демо — посилання або короткий фрагмент.

## Документи

- **Мова** — українська. **Формат** — Markdown, як на етапах 1–2.
- **Файли етапу** — у `docs/stages/stage-N/`.
- **Посилання** — відносні, як у наявних файлах: `[Product Map](../stage-2/Product-Map.md)`. Перед PR перевірте, що вони відкриваються на GitHub.
- **Джерела цифр** — у стилі репозиторію: (SWOT S1), (Decision), (Product Map).

## Якщо git ще незвичний

- **GitHub Desktop** робить усе те саме кнопками: гілка, коміт, push, PR.
- **Невелику правку в `.md`** можна зробити прямо на GitHub: олівець ✏️ → **Create a new branch** → назва гілки з ключем → **Propose changes**.
- **Застрягли більше ніж на 15 хвилин** — пишіть ліду. Це нормально.
